Devices for AI Agents

An open protocol for AI agents to own and use real devices. A laptop, a camera, a screen in the kitchen: signed, approved on the device itself, and with no cloud in the middle.

HOW IT WORKS GITHUB

Experimental specification. Companion to AMP (messages), AID (identity), AAP (UI actions) and AFP (files).

WHAT IT IS

What is ADP?

ADP defines how an AI agent uses a real device: take a picture, listen, show text or an image, speak. The agent's controller signs each request and sends it straight to the device. The device checks the signature, the owner and its local grants before it does anything.

Camera, microphone, speaker and screen output stay off until someone grants them on the device. A device with a camera or microphone shows a sign to people nearby whenever it captures.

THE IDEA

Agents live in terminals. People live in rooms.

ADP gives an agent a presence in the physical world without handing it the keys to your home.

THE RULES

Six rules

A device is optional

An agent with no device is complete. Most agents have none, and they need no device key.

Many devices, one active

An agent can own many devices and is active on at most one. It jumps between them. It never sees through two cameras at once.

One owner

A device has zero or one owner. The device's signed answer is the truth, not anyone's records.

The person at the device has the last word

Camera, microphone and speaker are off until granted there. Ownership changes wait for approval there. A controller cannot turn off the in-use sign.

No cloud, no relay

Device and controller talk directly, signed end to end with Ed25519.

Fixed operations only

No remote shell, no arbitrary files, no remote code. A controller cannot install, change or remove a handler on a device.

What ADP does not protect: a controller key is the agent's authority. Any program able to use that key can act as that agent, and a stolen key grants everything approved on the device.

ROLES

Device and controller

Device

Owns the hardware and the local grants. Answers signed requests. It decides who its owner is and what is allowed.

Controller

Acts for agents: keys, inventory, the active device, liveness. One process can serve many agents, and it signs for each agent with that agent's own key.

  • Pairing is local. The operator pins public keys on both sides before any network use. An unpaired peer cannot enroll itself over HTTP.
  • Two ways to connect. A device either answers on HTTP or opens its own WebSocket connection to the controller, which is how a device behind a home router or a phone reaches it. In v1 both run over loopback or a Tailscale path.
  • Jumps. A jump replaces the agent's active device at once, and the last accepted jump wins. Old operations are cancelled and their results are not delivered. Sensors, live media and output are refused on an idle device before any request is sent.
  • Input from the device. Text typed at a device reaches its owning agent, marked as device input. It never becomes a system instruction, and it does not prove who typed it.

HOW A REQUEST WORKS

One photo, step by step

  1. The agent asks its controller for camera.snapshot. The controller checks that the device is the active one and that it advertises the capability.
  2. The controller gets a challenge from the device. A challenge works once and expires after 30 seconds.
  3. The controller signs the request with the agent's key and posts it.
  4. The device verifies the pinned key, the target and the challenge, and uses up the challenge. A retry with the same challenge fails, even after a restart.
  5. The device checks the local camera grant, shows its in-use sign, captures, and signs the result.
  6. The controller verifies the signature and the matching id and challenge. The agent gets the picture.
GET  /v1/challenge
  -> {"challenge":"<48 hex characters>"}

POST /v1/request
     {"body":"<base64url>","signature":"<base64url>"}
     body decodes to:
     {"type":"invoke","id":"<48 hex>","challenge":"<48 hex>",
      "to":"<device key>","capability":"camera.snapshot"}

  -> {"body":"<base64url>","signature":"<base64url>"}
     body decodes to a result with the same id and challenge, to the controller key:
     {"type":"result","ok":true,
      "value":{"mime":"image/jpeg","data":"<standard base64>"}}

The Ed25519 signature covers the bytes of ai-maestro-device/1, one NUL byte, then the exact body bytes. No key inside a network message counts toward trust. The protocol began inside AI Maestro, and the signature domain is part of the wire format, so that name stays for v1.

If the device refuses, the signed result has ok:false and an error such as denied or hardware_unavailable. Invalid authentication, expired challenges and malformed packets get HTTP 403.

CAPABILITIES

What a device can offer

A device lists its capabilities in its signed registration. Each one declares its arguments and when it can run. A controller rejects anything undeclared.

CapabilityArgumentsLocal grantActivation
device.healthEmpty objectOwnershipany
camera.snapshotEmpty objectCamera and working visible indicatoractive
display.textText, up to 4096 UTF-8 bytesdisplay.textactive
display.imagemime (image/jpeg or image/png), standard base64 data, decoded maximum 256 KiBdisplay.imageactive
speaker.sayText, up to 500 UTF-8 bytesspeaker.sayactive
  • Output is plain. Text is literal text, never HTML or markup. Images must be real PNG or JPEG. SVG, URLs and file paths are refused. Output grants default to off.
  • Owner-defined capabilities. The device owner can install actions named custom.OWNER.ACTION. Each has bounded arguments, a timeout and its own local grant, off by default.
  • Live media. Video and microphone sessions run from 1 to 60 seconds, and every frame is signed. Video, microphone and speaker each have separate local consent.
  • The in-use sign. A device with a camera or microphone must show a sign to people nearby whenever it captures or streams. A hardware light tied to sensor power is preferred, and a visible local screen sign is the minimum. A device that cannot show a working sign must not offer capture.
  • Transfer resets grants. When a device changes owner, its media, output and custom grants all reset.

IMPLEMENTATIONS

What exists today

ComponentWhat it is
Linux bridgeThe device side: health, camera and audio, text, image and speech output, and owner-installed custom capabilities.
Reference controllerA small CLI and MCP controller with inventory, activation and optional AMP delivery.
Shared SDKA controller SDK for one server with many agents, over HTTP and device-opened WebSockets. It ships from the repo, not from a public npm release.

To check it on one computer, clone the repo, install Node.js 22 or newer, and run the tests. They start a real loopback HTTP bridge, with test adapters for the camera and AMP delivery.

git clone https://github.com/agentmessaging/agent-device-protocol.git
cd agent-device-protocol
npm ci --ignore-scripts
npm test
